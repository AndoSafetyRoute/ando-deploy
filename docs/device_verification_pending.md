# 실기기 검증 대기 목록

**S1~S6 개발·로컬(에뮬레이터/헤드리스/로컬 DB) 검증 완료(2026-09-17). 학습
보행(10건) 시작 전, 이 문서의 모든 항목이 "통과"로 표시돼야 한다.**
Docker(로컬 dev Postgres)·Android 에뮬레이터로 검증 가능한 것은 각 S-항목
커밋 시 이미 확인했고, 여기 남은 건 **실제 안드로이드 기기**(GPS 하드웨어,
OS 배터리 최적화, 실제 보행)에서만 확인 가능한 것들이다.

각 항목: 측정 방법 / 통과 기준 / 상태.

---

## 1. GPS 콜백 간격 (S0)

- **측정 방법**: 실기기로 10분 이상 실외 보행(안내 화면 유지) 1회 →
  `backend/scripts/gps_interval_report.py --session <session_id>` (로컬 dev DB
  기준. 운영 DB로 확인하려면 스크립트의 localhost 안전장치를 별도로 완화해야
  함 — 이 문서 작성 시점 기준 운영 DB 접근은 금지 상태이므로 로컬 dev DB로
  수집하는 실기기 테스트를 전제로 한다).
- **통과 기준**: 콜백 간격 중앙값 ≤ 2s.
- **상태**: ⬜ 대기 (에뮬레이터 간격은 실기기 판정 근거로 쓰지 않음 — geo fix는
  즉시 반영이라 OS 스케줄링 지연이 재현되지 않음).

## 2. BestForNavigation 실내·건물 인근 첫 위치 획득 시간

- **측정 방법**: 실내(또는 건물 밀집 지역)에서 안내 시작 → `[GPS] 첫 픽스 수신`
  로그의 `stage`/`ms`를 logcat 또는 `/collect/session/gps-fix` 서버 기록
  (`sessions.gps_fix_stage`, `sessions.gps_fix_ms`)으로 확인.
- **통과 기준**: (초안, C등급) `best_nav` 단계에서 15초 내 못 잡아도 `high`→
  `balanced`로 자동 전환돼 30초 내에는 첫 위치가 잡힘. 옛 `Accuracy.High`
  회피 사유(무한 대기)가 재현되지 않을 것.
- **상태**: ⬜ 대기 (에뮬레이터는 geo fix가 정확도 단계와 무관하게 즉시
  반영돼 "무한 대기" 상황 자체가 재현 안 됨 — 이 항목은 에뮬레이터로 검증
  불가능한 항목).

## 3. keep-awake 배터리 소모

- **측정 방법**: 실기기로 30분 이상 안내 진행 후 배터리 사용량(설정 →
  배터리) 확인, keep-awake 적용 전(구버전 빌드)과 비교.
- **통과 기준**: (미정 — 팀 논의 필요) 절대 기준이 없으므로 "체감상 무리
  없는 수준"인지 먼저 정성 평가, 필요하면 파일럿 참가자 안내에 "완충 후
  사용" 문구 추가 여부 결정.
- **상태**: ⬜ 대기.

## 4. foreground service 필요 여부 재판단

- **측정 방법**: 항목 1(콜백 간격)이 keep-awake만으로 목표를 달성하는지 먼저
  확인. 달성 못 하면 화면이 켜진 채로도 OS가 GPS 콜백을 계속 늦추는지(Doze
  단계가 화면 on 상태에서도 백그라운드 프로세스 우선순위를 낮추는 기종별
  차이 — 특히 삼성 등 제조사 배터리 최적화 커스텀) 확인.
- **통과 기준**: keep-awake만으로 중앙값 ≤2s 달성 시 foreground service
  불필요로 결론. 달성 못 하면 별도 스파이크로 foreground service(알림 상주)
  도입 여부 논의.
- **상태**: ⬜ 대기 (항목 1 결과에 종속).

## 5. distanceInterval=0의 실기기 배터리/콜백량 영향

- **측정 방법**: 정지 상태(신호 대기 등)에서 실기기 GPS 콜백이 실제로
  timeInterval(1000ms)마다 계속 오는지, 그로 인한 배터리/데이터 사용량이
  허용 범위인지 확인.
- **통과 기준**: 정지 중에도 콜백이 옴(공백 아님) AND 배터리 소모가 항목 3과
  별개로 과도하지 않음.
- **상태**: ⬜ 대기.

## 6. S1(걸음 수) 실제 센서 동작

- **측정 방법**: 실기기에서 `[StepTracker] 시작 성공` 로그 확인 + 실제 걸음
  수가 그럴듯하게 누적되는지(과장/과소 없는지) 확인.
- **통과 기준**: 센서 있는 실기기에서 `available=true`로 시작되고
  `stepsBetween()` 결과가 실제 보행량과 대략 맞음.
- **상태**: ⬜ 대기 (에뮬레이터는 걸음 수 센서가 없어 null fallback 경로만
  코드 검토로 확인, 이 세션에서 라이브 재기동 검증은 안 함 — Metro OOM
  재현 회피).

## 7. S4/S5(D 질문 구성 + 가장 힘든 구간) 화면 흐름

- **측정 방법**: 실기기(또는 재기동 안전한 에뮬레이터 세션)에서 안내 종료 →
  3버튼 문항(순위+대조 섞여서 나오는지, 몇 문항인지) → "가장 힘들었던 구간"
  화면 → RouteDetail 순서로 자연스럽게 넘어가는지 직접 확인.
- **통과 기준**: 화면 전환에 크래시/멈춤 없음, 지도 하이라이트가 선택에 맞게
  바뀜, 제출 후 RouteDetail 도달.
- **상태**: ⬜ 대기 (`tsc --noEmit` 통과 + 기존 검증된 패턴 재사용까지만
  확인, 이 세션에서 라이브 UI 테스트는 안 함 — Metro OOM 재현 회피).

## 8. S6 — facility(계단) 플래그 버그 수정 + slope_source 신뢰도 구분

- **배경**: 이번 패스에서 `NavigationScreen.tsx::normalizeSegments()`가
  `is_stairs`를 복사하지 않아 S6.5 이후 계단 구간에서도 신호 A의
  `facility` 플래그가 한 번도 `true`가 된 적이 없었던 버그를 발견·수정함
  (§config_reference.md S6 참고). 로직 수정 자체는 헤드리스 테스트로
  확인했지만, **실제 계단이 있는 경로를 실기기로 걸어야만** 이 수정이
  운영 조건에서 진짜로 동작하는지 확인된다(에뮬레이터는 실제 GPS 궤적이
  아니라 `adb emu geo fix`로 좌표를 주입하므로, 실제 경로의 계단 세그먼트를
  "통과하는" 실측 흐름 자체를 재현하기 까다로움).
- **측정 방법**: 계단이 포함된 경로로 실기기 보행 → 종료 후
  `trip_slope_observations`에서 해당 세션 행 조회 → 계단을 지난 행의
  `facility=true` 확인.
- **통과 기준**: 계단 구간을 포함한 행에서 `facility=true`가 실제로
  기록됨(이전엔 항상 `false`였음).
- **부가 확인(선택)**: 같은 조회에서 `slope_source` 값 분포도 같이 보고
  교량 구간이 있었다면 `bridge_zero`가 나오는지 육안 확인.
- **상태**: ⬜ 대기.

## 최종 정리 — 학습 보행 시작 전 실기기 검증 패키지

**S1~S6(신호 A~D 파이프라인 전체) 개발/로컬 검증 완료.** 아래는 실제 보행
전에 팀에서 확인해야 할 것 전부를 한 곳에 모은 것.

### EAS 빌드 필요 여부

이번 S1~S6 작업에서 **새로 추가된 네이티브 의존성은 없음** — `expo-sensors`
(S1, 걸음 수)와 `expo-keep-awake`(S0, 화면 꺼짐 방지)는 이미 이전 커밋
(`4e8ccdf`, `384d393`)에서 `package.json`에 들어갔고 이번 패스에서 변경하지
않았다. S2~S6은 전부 순수 JS/TS 로직(스토어/컴포넌트/유틸)과 백엔드
Python/SQL 변경뿐이라 네이티브 재빌드 트리거가 없다.

다만 다음 두 가지는 **이미 과거에** 네이티브 재빌드가 필요했던 변경이라
(이번 패스가 아니라 S0/S1 커밋 시점), 그 이후로 한 번도 EAS 빌드를 안
돌렸다면 지금 실기기 테스트 전에 필요하다:
- `expo-sensors`(걸음 수 센서) — Expo Go에 포함돼 있는지 SDK 54 기준 재확인 필요(포함돼 있으면 커스텀 빌드 불필요).
- `ACTIVITY_RECOGNITION` 권한(Android 매니페스트) — 매니페스트 변경은 OTA/JS 업데이트로 반영 안 됨, 반드시 네이티브 빌드에 포함돼야 함.

**결론(팀원 확인 필요)**: 현재 실기기에 깔린 빌드가 `384d393`(S1, 걸음 수
커밋) 이후 빌드인지 확인 — 맞으면 이번 S2~S6 변경은 OTA(JS 번들 갱신)만으로
충분. 아니라면 그 커밋 이후 최소 1회 EAS 빌드가 필요. **빌드 실행/배포
자체는 팀원 담당**(요청 메모 반영) — 여기서는 필요 여부 판단 근거만 남긴다.
백엔드 배포(운영 서버 `SUBWAY_DATA_DIR` 경로 포함)도 마찬가지로 팀원 담당.

### 실기기 보행 시 확인할 체크리스트

한 번의 실외 보행(가능하면 계단 1곳 이상 포함된 경로, 10분 이상)으로
아래 항목을 한 번에 확인할 수 있다:

1. [ ] 안내 화면이 꺼지지 않는다(keep-awake, 항목 3).
2. [ ] GPS 콜백이 자주 온다 — 체감상 멈칫거림 없이 화살표/진행률이 갱신됨(항목 1, 4, 5).
3. [ ] 실내/건물 인근 출발 시 첫 위치가 30초 이내에 잡힌다(항목 2).
4. [ ] 걸음 수 관련 크래시/경고 로그가 없다(항목 6).
5. [ ] 계단 구간을 실제로 지나간다(항목 8 — facility 버그 수정 확인용, 가능하면 포함).
6. [ ] 안내 종료 후 3버튼 문항(순위+대조 섞임) → "가장 힘들었던 구간" 화면 → RouteDetail로 자연스럽게 전환된다(항목 7).
7. [ ] 보행 중/후 배터리 소모가 체감상 과하지 않다(항목 3, 5).

### 검증 후 실행할 스크립트 (로컬 dev DB, `DATABASE_URL=...@localhost:5433/ando_dev` 필수)

보행이 끝나면 세션 ID(로그 또는 `sessions` 테이블에서 `started_at` 기준
최신 행)를 확인한 뒤:

```bash
# 1) GPS 콜백 간격 (항목 1)
python backend/scripts/gps_interval_report.py --session <session_id>

# 2) facility/slope_source 버그 수정 확인 (항목 8) — 직접 조회
psql "$DATABASE_URL" -c "
  SELECT id, distance_m, facility, slope_source, slope_mean
  FROM trip_slope_observations
  WHERE session_id = '<session_id>'
  ORDER BY id;
"

# 3) gps_fix_stage/gps_fix_ms 확인 (항목 2)
psql "$DATABASE_URL" -c "
  SELECT session_id, gps_fix_stage, gps_fix_ms
  FROM sessions WHERE session_id = '<session_id>';
"
```

이 실기기 보행 데이터는 `sessions.phase` 기본값이 `'free'`라 위 8개 항목
전부 "통과"로 바뀌기 전까지는 **파일럿 학습 데이터로 집계되지 않는다**
(`learning_rows_v`는 `phase='learning'`만 포함) — 검증용 보행이 실수로
학습 데이터에 섞일 위험이 없다.

## 참고 — 에뮬레이터로 이미 확인한 것 (이 문서에 포함 안 됨)

아래는 에뮬레이터(Docker 로컬 dev DB + Android 에뮬레이터 + `adb emu geo fix`)로
검증 가능해 각 S-항목 커밋 보고에 결과가 있음 — 여기서 중복 기재하지 않음:
- distanceInterval=0으로 정지 중에도 콜백이 오는지(에뮬레이터 GPS 스택 기준)
- fallback 단계 전환 로직 자체의 동작(코드 경로 — 단, "왜 전환이 필요한
  상황"인 실내 무한대기는 에뮬레이터로 재현 불가, 위 항목 2 참고)
- keep-awake 코드 적용 여부(`dumpsys power`의 wake lock 확인)
- 궤적 재생 하네스(T)로 검증한 A/D 판정 로직(정지/공백/점프/저속 시나리오)
