# 실기기 검증 대기 목록

**학습 보행(10건) 시작 전, 이 문서의 모든 항목이 "통과"로 표시돼야 한다.**
Docker(로컬 dev Postgres)·Android 에뮬레이터로 검증 가능한 것은 각 S-항목
커밋 시 이미 확인했고, 여기 남은 건 **실제 안드로이드 기기**(GPS 하드웨어,
OS 배터리 최적화, 실제 보행)에서만 확인 가능한 것들이다.

각 항목: 측정 방법 / 통과 기준 / 상태.

---

## 1. GPS 콜백 간격 (S0)

- **측정 방법**: 실기기로 10분 이상 실외 보행(안내 화면 유지) 1회 →
  `backend/scripts/gps_interval_report.py --session <session_id>` (로컬 dev DB
  기준. 운영 DB로 확인하려면 스크립트의 localhost 안전장치를 별도로 완화해야
  함 — 이 문서 작성 시점 기준 운영 DB 접근은 금지 상태이므로 로컬 dev DB로
  수집하는 실기기 테스트를 전제로 한다).
- **통과 기준**: 콜백 간격 중앙값 ≤ 2s.
- **상태**: ⬜ 대기 (에뮬레이터 간격은 실기기 판정 근거로 쓰지 않음 — geo fix는
  즉시 반영이라 OS 스케줄링 지연이 재현되지 않음).

## 2. BestForNavigation 실내·건물 인근 첫 위치 획득 시간

- **측정 방법**: 실내(또는 건물 밀집 지역)에서 안내 시작 → `[GPS] 첫 픽스 수신`
  로그의 `stage`/`ms`를 logcat 또는 `/collect/session/gps-fix` 서버 기록
  (`sessions.gps_fix_stage`, `sessions.gps_fix_ms`)으로 확인.
- **통과 기준**: (초안, C등급) `best_nav` 단계에서 15초 내 못 잡아도 `high`→
  `balanced`로 자동 전환돼 30초 내에는 첫 위치가 잡힘. 옛 `Accuracy.High`
  회피 사유(무한 대기)가 재현되지 않을 것.
- **상태**: ⬜ 대기 (에뮬레이터는 geo fix가 정확도 단계와 무관하게 즉시
  반영돼 "무한 대기" 상황 자체가 재현 안 됨 — 이 항목은 에뮬레이터로 검증
  불가능한 항목).

## 3. keep-awake 배터리 소모

- **측정 방법**: 실기기로 30분 이상 안내 진행 후 배터리 사용량(설정 →
  배터리) 확인, keep-awake 적용 전(구버전 빌드)과 비교.
- **통과 기준**: (미정 — 팀 논의 필요) 절대 기준이 없으므로 "체감상 무리
  없는 수준"인지 먼저 정성 평가, 필요하면 파일럿 참가자 안내에 "완충 후
  사용" 문구 추가 여부 결정.
- **상태**: ⬜ 대기.

## 4. foreground service 필요 여부 재판단

- **측정 방법**: 항목 1(콜백 간격)이 keep-awake만으로 목표를 달성하는지 먼저
  확인. 달성 못 하면 화면이 켜진 채로도 OS가 GPS 콜백을 계속 늦추는지(Doze
  단계가 화면 on 상태에서도 백그라운드 프로세스 우선순위를 낮추는 기종별
  차이 — 특히 삼성 등 제조사 배터리 최적화 커스텀) 확인.
- **통과 기준**: keep-awake만으로 중앙값 ≤2s 달성 시 foreground service
  불필요로 결론. 달성 못 하면 별도 스파이크로 foreground service(알림 상주)
  도입 여부 논의.
- **상태**: ⬜ 대기 (항목 1 결과에 종속).

## 5. distanceInterval=0의 실기기 배터리/콜백량 영향

- **측정 방법**: 정지 상태(신호 대기 등)에서 실기기 GPS 콜백이 실제로
  timeInterval(1000ms)마다 계속 오는지, 그로 인한 배터리/데이터 사용량이
  허용 범위인지 확인.
- **통과 기준**: 정지 중에도 콜백이 옴(공백 아님) AND 배터리 소모가 항목 3과
  별개로 과도하지 않음.
- **상태**: ⬜ 대기.

## 참고 — 에뮬레이터로 이미 확인한 것 (이 문서에 포함 안 됨)

아래는 에뮬레이터(Docker 로컬 dev DB + Android 에뮬레이터 + `adb emu geo fix`)로
검증 가능해 각 S-항목 커밋 보고에 결과가 있음 — 여기서 중복 기재하지 않음:
- distanceInterval=0으로 정지 중에도 콜백이 오는지(에뮬레이터 GPS 스택 기준)
- fallback 단계 전환 로직 자체의 동작(코드 경로 — 단, "왜 전환이 필요한
  상황"인 실내 무한대기는 에뮬레이터로 재현 불가, 위 항목 2 참고)
- keep-awake 코드 적용 여부(`dumpsys power`의 wake lock 확인)
- 궤적 재생 하네스(T)로 검증한 A/D 판정 로직(정지/공백/점프/저속 시나리오)
